# 如何写出优秀的 Skill

## 我们在学什么

Skill 不是一段更长的提示词，而是一份给 Agent 使用的工作说明书。它规定什么时候启动、执行时按什么路径推进、何时算完成，以及哪些资料只在需要时才读取。

它与相邻概念的区别：

- 提示词：一次性的请求，例如“帮我总结这篇文章”。
- Skill：可反复使用的做事方法，例如“每次学习文章时先读原文、区分证据与推导、再帮助我主动提取”。
- 工具：实际执行外部动作的能力，例如搜索网页、读取 X、创建文件。

一句话：Skill 决定 **怎么做**，工具决定 **能做什么**。

## 核心问题

怎样写出一个让 Agent 稳定遵循正确工作过程的 Skill，而不是一份越写越长、却越来越难用的提示词？

## 核心框架

### 1. Trigger：什么时候启动

先判断由谁启动。

- 手动触发：由用户明确说出要使用某个 Skill。适合需要人为判断、并非每轮都发生的任务；不会增加长期上下文负担。
- 自动触发：模型根据用户意图自行发现并调用。适合必须自动介入的任务；代价是触发描述会持续占用上下文与注意力。

初学原则：先写手动触发的 Skill。只有模型必须自行发现、或其他 Skill 必须调用它时，再做自动触发。

### 2. Structure：步骤与资料分层

主文件只放 Agent 在当前任务中必须执行的内容：

- `steps`：每次都要做的动作。
- `reference`：仅特定分支或特定细节需要时才读取的资料。

不要把主文件写成百科全书。判断一句内容放在哪里的标准是：**Agent 现在必须看到它吗？**

### 3. Steering：怎样让 Agent 不跑偏

每一步都应写清动作和完成标准。

- 模糊：`检查一下改动。`
- 清晰：`逐一确认所有被修改的模型都有对应测试；缺失者列为未完成。`

完成标准应尽量满足两个条件：

- 可检查：能判断完成还是未完成。
- 有覆盖要求：不会只做一个例子就提前结束。

可以使用高密度的 leading word 锚定行为，例如 `evidence-first`、`red`、`tracer bullets`。好的 leading word 是模型已经理解、且任务中确实有用的概念；它不是装饰性的口号。

优先正向描述目标行为：与其写“不要写冗长注释”，不如写“注释保持一行，解释原因”。

### 4. Pruning：持续删减

每次修改或使用后，逐句检查：

- 这句话是否还与任务相关？
- 它是否与别处重复？
- 它是否已经过时？
- 删掉它，Agent 的行为会改变吗？

需要删除或处理的典型问题：

- 重复：同一含义出现多次。
- 沉积：过去有用、现在失效的内容。
- 蔓延：每句都有效，但主文件仍过长。
- 无效指令：模型默认就会做，写了不改变行为。

## 写作流程

1. 选一个会反复发生、且容易出错的真实任务。
2. 说清它的输入、期望结果与边界。
3. 决定手动还是自动触发。
4. 写出 3～5 个必经步骤。
5. 给每一步补一个可检查的完成标准。
6. 将分支性资料移到单独的参考文件。
7. 在一个真实任务中运行它。
8. 根据实际失败补规则；根据冗余删规则。

## 最小模板

```markdown
---
name: <技能名称>
description: <它做什么；若自动触发，简要写明触发场景>
---

# <行为主导词>

## 目标

要让 Agent 稳定完成的事情。

## 步骤

1. <动作>
   - 完成标准：<如何判断已经做好>

2. <动作>
   - 完成标准：<如何判断已经做好>

## 条件参考资料

只有在 <明确条件> 下，读取 [参考资料](./reference.md)。
```

## 一个小例子：学习一篇 AI 文章

```markdown
---
name: 学习 AI 文章
description: 帮我用结构化方式学习一篇文章。
disable-model-invocation: true
---

# Evidence-first

## Goal

把文章转化为可理解、可检验、可复用的知识。

## Steps

1. 读取文章原文。
   - 完成标准：确认已得到完整正文；若只有片段，明确说明。

2. 提取核心问题、主要主张与证据。
   - 完成标准：每条主张标记为“原文内容”或“推导”。

3. 用白话解释关键概念。
   - 完成标准：每个概念包含一句定义、一个例子和一个边界。

4. 提出一个主动提取问题。
   - 完成标准：问题能检验理解，而不是只问“懂了吗”。
```

## 原文中的好与不好例子

以下内容依据 [Matt Pocock 的原始文档](https://github.com/mattpocock/skills/blob/main/skills/productivity/writing-great-skills/SKILL.md) 整理；短语示例保留英文，是为了对应作者的术语。

### 触发描述：重复同义词不是更多触发条件

【原文内容】作者用 TDD 描述举例：把“用 TDD 构建功能”和“要求 test-first development”都写进触发描述，实质上是在重复同一个分支。

- 不好：为一个意图堆叠多个近义触发词。
- 好：一个真实分支保留一个触发条件；只有任务路径确实不同，才增加分支。

### 完成标准：可检查且有覆盖范围

【原文内容】作者对比“产出变更列表”和“每个被修改的模型都被处理”。前者只要求给出一个产物，后者明确了覆盖范围，因此更能驱动 Agent 做足准备工作。

- 不好：`产出一个变更列表。`
- 好：`每个被修改的模型都已被处理。`

### 行为主导词（leading word）：把一串抽象要求压缩成一个已有概念

【原文内容】作者给出的两个压缩例子：

- “快速、确定、低开销”可以压缩为“紧凑”（原文：`tight`）。
- “一个你相信的循环”可以压缩为“变红”（原文：`red`），因为 bug 是否已经让循环变红是可观察的状态。

这里的关键不是英语词本身，而是选择模型已经理解、能稳定激活一组行为的概念。

### 无效指令（no-op）：相关不等于有用

【原文内容】“请彻底处理”（原文：`be thorough`）可能没有改变模型默认行为，因此可能是无效指令；作者建议用更有区分度的词，例如“毫不松懈”（原文：`relentless`），并通过实际运行验证行为是否真的变化。

### Negation：不要把错误模式放进注意力中心

【原文内容】作者用“不要想象大象”的心理图像说明：禁令会把被禁止的模式带进上下文。若目标是简洁注释，与其强调“不要冗长”，不如直接要求“一行注释”。

## AI 编写的练习例子

以下例子是【AI 编写的练习例子】，用来解释原则；不是 Matt Pocock 的原文，也不是你的个人观点。

### 触发：不把所有事都交给自动触发

不好的写法：

```markdown
description: 用户只要提到文章、视频、学习、总结、知识，就自动使用本 Skill。
```

问题：触发范围过大。用户可能只是随口提到一篇文章，并不希望进入完整学习流程；这个描述还会长期占用 Agent 的注意力。

较好的写法：

```markdown
description: 当用户明确要求通过引导问题和练习来学习一篇已提供的文章或视频时使用。
```

为什么更好：触发条件具体，且只包含真正不同的任务分支。若这个流程只会由用户明确发起，更适合改为手动触发。

### 结构：不把主文件写成说明书全集

不好的写法：

```markdown
## 步骤

1. 阅读材料。
2. 阅读 50 条关于引用格式、视频字幕、图书、论文、播客、网页、术语解释和复盘方式的规则。
3. 开始学习。
```

问题：执行步骤被大量背景资料淹没，Agent 不容易抓住当前真正要做的事。

较好的写法：

```markdown
## Steps

1. 确认是否能访问完整材料。
   - 完成标准：已获得全文，或明确说明材料不完整。

2. 提取核心问题、主张和证据。
   - 完成标准：每条主张都标记来源。

## 条件参考资料

当材料是视频时，读取 [视频转录规则](./视频转录规则.md)。
当需要引用时，读取 [来源标注规则](./来源标注规则.md)。
```

为什么更好：所有路径都需要的动作在前面；只在特定情况需要的资料被按需读取。

### 引导：把“认真”改成可检查的行为

不好的写法：

```markdown
请仔细、全面、高质量地分析文章。不要遗漏细节，也不要胡说。
```

问题：这些词很抽象，完成与否不可检查；其中一部分还是模型的默认行为，未必改变结果。

较好的写法：

```markdown
# Evidence-first

1. 列出不超过五条核心主张。
   - 完成标准：每条主张附一条原文证据；无证据者标为“推导”。

2. 对每个关键概念给出一句白话定义、一个例子和一个不适用的边界。
```

为什么更好：`Evidence-first` 给出稳定的行为方向；其余要求既可观察，也能判断是否已经完成。

### 剪枝：删掉重复与无效指令

不好的写法：

```markdown
请务必检查所有来源。
一定要仔细核查引用。
不要遗漏任何来源。
确保引用没有问题。
```

问题：四句话表达几乎同一个意思，既占用注意力，也可能让这一条规则获得不合理的权重。

较好的写法：

```markdown
核对每条外部事实是否有可访问来源；没有来源的内容标为“待验证”。
```

为什么更好：保留一个权威表述，并给出具体动作与失败处理方式。

## 学习状态

- 用户的旧理解：尚未记录。不要把 AI 的推测当作用户观点。
- 当前已确认的理解：优秀 Skill 通过触发、信息层级、执行引导和持续剪枝，帮助 Agent 更可预测地完成任务。
- 待验证：把一个真实、高频任务写成小 Skill 后，这套结构是否能实际减少遗漏与返工。

## 下一次实践

选择一个真实、高频且容易遗漏步骤的任务，先写一个不超过五步的手动触发 Skill；运行一次后再依据实际失误修订。
